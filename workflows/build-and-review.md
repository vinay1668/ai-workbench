# Build and review workflow

## 1. Define a useful result

Choose one primary user journey. Fill the [brief](../templates/product-brief.md). Write observable criteria before building. For a document, substitute the reader's decision and required content for the app journey.

## 2. Supply a small context pack

Attach relevant source facts, one good example, and the applicable constraints. Annotate screenshots. If you supply two references, explain which qualities should come from each. Do not upload unrelated files to make the prompt look thorough.

## 3. Choose a procedure

For a website, use one design direction and one review procedure. For a research task, specify evidence requirements. For repeated work, use a reusable prompt or skill if it fits. Start with the [catalog](../CATALOG.md); do not install everything.

## 4. Build a complete small output

Finish the main journey or deliverable, including meaningful failure states. Distinguish mock data and demo integrations from real ones. Ask for actual files when you need an artifact rather than an explanation of how to create one.

## 5. Inspect what the user will see

Open the artifact, inspect the rendered document, or exercise the running app. Check a normal input and an edge case. For a website, inspect small and large screens and keyboard interaction. When the necessary tools are unavailable, mark the check as pending.

## 6. Revise based on evidence

Supply a screenshot, concrete reproduction, or rubric finding. Target the most consequential defect first. “The mobile navigation covers the submit button at 390px” gives clearer direction than “make it better.”

## 7. Keep the reusable part

Save the generalized prompt, sanitized example, reference annotations, and verification notes. Remove task-specific personal details. Prefer a small repeatable pack over an entire conversation dump.
